# dsh-evolve-in-git 记忆插件设计思考（README「Principal」原文）

## Principal

一、设计记忆插件需要考虑的关键问题

1. 记忆的存储结构

· 短期记忆：当前会话上下文、最近 N 轮对话。
· 长期记忆：跨会话持久化的信息。
· 工作记忆：当前任务临时需要的中间状态。

你需要决定：

· 长期记忆存哪里？本地文件、SQLite、向量数据库、云端？
· 是否区分"用户级记忆""项目级记忆""全局记忆"？
· 记忆是结构化 JSON，还是自然语言片段，还是 embedding 向量？

---

2. 记忆的写入时机

不能什么都说"记住"。需要触发策略：

· 显式触发：用户说"记住……""以后都这样"。
· 隐式触发：模型判断当前信息具有长期价值，例如用户提到"我在用 React 19，偏好函数组件"。
· 周期性整理：会话结束后自动总结关键信息并写入长期记忆。
· 阈值触发：某类信息重复出现 N 次才写入，避免噪声。

---

3. 记忆的检索方式

记忆写进去后，怎么在需要时取出来？

· 关键词检索：BM25、全文索引。
· 语义检索：embedding + 向量相似度。
· 混合检索：先语义召回，再用规则过滤。
· 时间衰减：越近的记忆权重越高。
· 主动注入：每次新会话开始时，自动加载与该用户/项目最相关的 Top-K 条记忆。

关键问题：检索粒度是"条"，还是"段"，还是"图谱节点"？

---

4. 记忆的更新与冲突处理

同一个事实可能被更新或推翻：

· 用户说"我现在住在北京"，但旧记忆是"住在上海"。
· 需要支持：覆盖、合并、版本化、置信度标记。
· 冲突时是否询问用户？还是自动采用最新信息？

例如：

```json
{
  "key": "用户居住地",
  "value": "北京",
  "updated_at": "2026-08-28",
  "confidence": 0.9,
  "source": "用户原话"
}
```

---

5. 记忆的遗忘机制

不是所有记忆都该永久保留。

· 过期记忆：例如"本周五要交报告"，过了时间就应降权或删除。
· 低价值记忆：很少被检索到的记忆可以归档。
· 用户主动删除：用户说"忘掉我上次说的那个偏好"。
· 容量限制：设置每个用户最多 N 条长期记忆，超出后按重要性/时间淘汰。

---

6. 隐私与安全

记忆插件会持久化用户数据，必须考虑：

· 敏感信息识别：电话、地址、密码、身份证号等是否默认不记？
· 用户控制：允许查看、导出、删除记忆。
· 加密存储：本地可加密，云端必须加密。
· 权限隔离：不同用户/项目的记忆不能混淆。
· 合规：GDPR 的被遗忘权、数据最小化原则。

---

7. 记忆的格式与可解释性

· 记忆应该是人和模型都能读懂的，便于调试和用户审查。
· 避免只存 embedding 而丢失原始文本。
· 建议格式：{id, type, content, metadata, created_at, updated_at, importance, source}

---

8. 与 DeepSeek harness 的集成方式

· 记忆插件是作为工具调用，还是中间件拦截所有请求？
· 是在 prompt 前自动插入记忆，还是让模型决定何时查询记忆？
· 是否支持多轮对话中动态调用 memory_search、memory_save、memory_update、memory_delete？

一个常见的架构：

```
用户输入 → 记忆检索器 → 注入相关记忆到 system prompt → 主模型生成 → 记忆写入器 → 保存有价值信息
```

---

9. 成本与性能

· 每次检索记忆会增加 token 消耗和延迟。
· 向量数据库和 embedding 计算有成本。
· 需要在"记忆带来的上下文提升"和"额外开销"之间平衡。
· 可以设置记忆注入上限，例如每次最多注入 10 条、每条不超过 200 字。

---

二、哪些要素适合作为记忆

不是所有对话内容都值得记。适合作为长期记忆的要素通常具有跨会话复用价值、稳定性、个性化。

1. 用户偏好与习惯

· 语言风格：喜欢简洁回答 / 详细解释 / 用表格。
· 格式偏好：输出用 Markdown、JSON、YAML。
· 工具偏好：喜欢用 Python 而不是 Node。
· 交互习惯：不喜欢寒暄，直接给结论。

例：用户偏好：回答使用中文，代码示例用 TypeScript，解释要带原理说明。

---

2. 稳定事实信息

· 用户身份：职业、角色、技术水平。
· 环境信息：操作系统、开发框架、硬件配置。
· 长期项目背景：正在开发什么产品、目标用户是谁。

例：用户是一名后端工程师，主要使用 Go 和 PostgreSQL，正在开发一个电商中台。

---

3. 项目上下文与约束

· 项目目标、范围、非目标。
· 技术选型决策及原因。
· 命名规范、目录结构约定。
· 已知限制或不可更改的约束。

例：项目"X"必须兼容 iOS 15，不能使用 SwiftUI 新特性。

---

4. 决策与原因

不只是记住"选了什么"，还要记住"为什么选"。

· 为什么放弃某个方案。
· 用户对某类解决方案的态度。

例：用户拒绝使用微服务架构，理由是团队规模小、维护成本高。

---

5. 关系与实体

· 人名、角色、团队关系。
· 组件之间的依赖关系。
· 第三方服务账号对应的用途。

例：小王负责前端，小李负责数据；前端通过 BFF 层调用后端。

---

6. 长期目标与计划

· 季度目标、学习计划、迁移计划。
· 用户关注的技术方向。

例：用户计划在 2026 年 Q4 将系统从 REST 迁移到 GraphQL。

---

7. 反馈历史与纠错记录

· 用户曾经纠正过模型的错误。
· 用户对某类回答的负面反馈。

例：用户提醒过：解释概念时不要用过度简化的类比。

---

8. 术语表与缩写

· 项目内部专有名词。
· 用户常用的缩写含义。

例："OM"在用户项目中指 Order Management，不是 Object Model。

---

9. 临时但重要的任务状态

· 当前正在进行的任务、待办事项、截止日期。
· 这类记忆需要设置过期时间或完成后自动清除。

例：截至 2026-08-28，用户正在修复支付回调的并发问题，尚未完成。

---

三、一个记忆条目的理想结构示例

```json
{
  "id": "mem_8f2a1",
  "type": "user_preference",
  "content": "回答时优先使用中文，代码示例用 TypeScript",
  "importance": 0.85,
  "created_at": "2026-08-28T10:00:00Z",
  "updated_at": "2026-08-28T10:00:00Z",
  "last_accessed_at": "2026-08-28T12:30:00Z",
  "expires_at": null,
  "source": "用户原话",
  "confidence": 0.95,
  "tags": ["语言", "代码风格"]
}
```

---

四、总结

设计 DeepSeek harness 记忆插件，核心要解决的问题是：

1. 存什么——只存高价值、跨会话、稳定的信息。
2. 怎么存——结构化、可检索、可更新、可删除。
3. 何时用——在合适的时候自动注入，不干扰正常对话。
4. 怎么忘——有过期、降权、删除机制。
5. 用户可控——透明、可审查、可纠正。

适合作为记忆的要素是那些具有长期复用价值、体现用户个性化、能减少重复沟通成本的信息，而不是一次性的对话细节。
